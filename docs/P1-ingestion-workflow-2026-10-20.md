# 字段映射、隔离入库与批次对账

2026-10-20，开发版新增。尚未重新打包发布，公开 beta.5 不包含本功能，也不包含上一轮同步向导。用户尚未开通抖店应用；本轮只使用合成数据，真实平台调用为0。

## 当前可操作的一条线

**经营分析 → 平台接入 → 配置连接 → 只读检查 → 拉取并加密暂存 → 任务「映射与入库」 → 保存映射 → 入库预览 → 确认入库 → 批次对账 → 交易与退款查看事件。**

开发已覆盖这条本地链路；真实店铺字段、支付/售后来源与后台完整性仍未验收，不能据此宣布 P1 或整个 PRD 完成。

## 本轮实现

| 环节 | 行为 | 位置 |
| --- | --- | --- |
| 来源字段检查 | 只返回抽样字段名及数组路径，不把原始页或个人字段值返回界面 | `ingestion.ts`、主进程 `retail-sync.ts` |
| 显式映射 | 15个必填交易字段、可选换货原行关联、事件数组及类型枚举、金额/时间单位；语义确认后保存不可变版本 | `ingestion-contract.ts`、`IngestionPanel.tsx` |
| 金额与时间 | 整数分或精确元字符串；ISO带时区或显式Unix单位；不猜单位、不默认缺数为0、不接受精度不安全的数字ID | `ingestion.ts` |
| 质量隔离 | 任一子事件错误隔离整条来源记录；同一事件ID内容冲突隔离相关记录；账本或事件链冲突阻止整批入库 | `ingestion.ts`、既有 `TransactionStore` |
| 去重 | 来源/店铺/渠道/事件ID构成业务键；批内和已有账本的相同事件去重，重复确认只有一份回执 | `ingestion-store.ts` |
| 预览与确认 | 冻结映射版本、暂存摘要和账本状态；变化后旧预览失效；预览本身不写交易事件 | `ingestion-store.ts` |
| 部分入库 | 显式勾选并填写至少10字原因；隔离记录保留，结果仍显示差异，修复后新批次只补缺少事件 | `IngestionPanel.tsx`、入库服务 |
| 原子落库 | 交易事件、交易批次及入库回执处于同一SQLite事务；回执失败会回滚事件，避免已记账却无回执 | `transaction-store.ts`、`ingestion-store.ts` |
| 批次对账 | 比较冻结事件键、账本值及独立合计；支持独立合成控制总额或人工参考合计；缺参考显示待核验 | `ingestion-store.ts`、界面对账区 |
| 留档 | 映射、预览、回执、对账历史持久化且不可覆盖；重启可查看 | 同上 |

演练采用7条合成来源记录、22个明确事件，含下单、支付、发货和跨日退款。新增「金额与规格错误」场景：2条错误来源记录隔离，16条有效事件可经确认入库。它们不是抖店官方字段样例。

真实模式没有预置猜测字段。即使手工映射成功，也仅写入 CSV 交易账本，来源标记 `operator_declared / unverified_declaration / partial`；店铺ID须与任务创建时冻结的声明一致，该检查不证明平台店铺身份已认证。订单列表快照不足以推断完整支付和售后事件，缺少明确事件时保持隔离。

## 对账含义与限制

对账对象是**本批冻结事件集合的合计**，不是全店结算期，也不是平台认证证明。人工填写的独立参考须注明来源、观测时间、店铺及8项合计，金额单位为分；不能把当前预览自动复制成“独立参考”。缺少参考时只检查账本，结果为待核验。隔离记录存在、事件不一致或任何合计差异都会显示差异。

交易入库不会自动补出毛利成本、库存观测或广告归因。退款也不会自动回补可售库存。演练数据进入演示交易来源，真实模式进入CSV交易来源；不进入三场景快照指标。

当前显示最近30个预览/回执和50个对账结果，数据仍保留在本地数据库。旧预览超出最近30项后需重新生成再确认。单次映射最多10,000条来源记录、100,000条事件，暂存批次上限24MB；账本沿用100,000事件容量限制。这不是大规模增量同步的性能验收。

## 验收

实际隔离 Electron 流程通过：

1. 从配置向导拉取错误演练数据，界面检查字段、保存映射；预览16条有效事件、隔离2条来源记录，预览后账本仍为空。
2. 未明确允许部分入库的请求被服务端拒绝；界面勾选并填写原因后入库16条，对账发现参考22、实际16。
3. 修复后的演练批次新增6条、去重16条，账本共22条，与独立合成控制总额一致。
4. 重复拉取新增0、重复22；重复确认仅一份回执。
5. 实际退出重启，映射/3份回执/对账历史及22条账本事件保留；独立人工参考故意多1分，准确显示差异，并保留人工声明标识。Renderer不能调用内部入库协议。

领域测试覆盖上述逻辑，并验证映射/暂存/账本变化使预览失效、不可覆盖冲突事件、精确金额及ID边界、店铺错配、实时模式缺独立参考、完整记录隔离、批内重复计数，以及注入回执写入故障后交易事件和批次全部回滚。

结果、类型检查、构建及桌面证据见 [验收归档](verification/ingestion-workflow-2026-10-20/report.md)。无真实模型调用，不计入模型质量评测。

## 剩余开发顺序

**抖店应用与只读授权 → 当前官方文档及脱敏响应核对 → 平台订单/支付/售后专用映射 → 多次增量补拉与实体变化处理 → 独立后台对账及来源完整性 → 真实目录/成本/库存/广告 → 可信多人审批 → 单独评审真实写入与效果观察。**

同步增量调度、自动Token续期、多店铺连接、暂存清理、完整对账单文件导入及逐行平台差异定位仍待开发。外部干净Windows、其他Windows版本及签名验收缺口继续保留。
